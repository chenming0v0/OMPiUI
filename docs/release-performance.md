# 发版速度与预构建

目标是将 **已有同源码预构建时，从推送 tag 到所有发布附件可下载** 的时间压到 5 分钟以内。GitHub runner 排队、网络传输不受仓库控制；首次冷构建、强制重建和没有匹配预构建的发布不承诺这个时限。

## 发布流程

1. 推送到默认分支 `dev` 后，`Desktop And Mobile Release` 自动预构建 Windows、macOS、Linux 的安装版与便携版，以及已配置签名密钥时的两种 Android APK。预构建不会创建 GitHub Release。
2. 确认该次工作流成功，再按正常流程将 `dev` 合并到 `main`，在 `origin/main` 上打 `v*` tag。
3. tag 工作流比较 Git 源码树。合并提交的 SHA 可以不同，但源码、版本、配置和工作流文件必须完全相同，才能复用产物。
4. 命中时跳过全部编译，从同一次成功的 `dev` 运行下载完整产物并发布；不再等待 Rust、Go 或 Gradle 编译。
5. 未命中时自动从目标 tag 的提交构建。解析结果与采用的路径写在工作流 Summary 中。

产物保留 14 天，查询最近 30 次成功的 `dev` push。过期、缺少平台、构建未完成、源码变化均会回退到正常构建。不会混用多次运行的附件，也不会复用 PR 或手动运行的产物。

手动执行工作流可以指定 `tag`；留空时选最新 `v*` tag。勾选 `rebuild` 会强制重建，适用于更新签名密钥或希望更新外部构建环境的情况。手动指定旧 tag 时，源码和 changelog 都从该 tag 读取。

## 构建阶段的优化

- 同一平台只构建一次服务端，安装版和便携版共享这份产物。
- 前端只构建一次，CI 用临时 Tauri 配置关闭重复的 `beforeBuildCommand`；本地普通构建不受影响。
- Android 只构建协议包与前端，不再构建桌面服务端、worker、relay 和 admin。
- `dev` 预构建与 tag 构建使用相同的 Rust 缓存标识。GitHub 允许 tag 恢复默认分支缓存，避免缓存只存在于各自的 tag 中。Rust 缓存只在 `dev` 保存。
- Android Tailscale AAR 按架构、Go 源码、模块依赖、NDK 版本与构建脚本缓存；命中时跳过 Go 工具安装和 AAR 编译。
- 已压缩的安装包上传 Actions artifact 时关闭二次压缩。

完整编译提前发生在 `dev` 上，因此会增加 `dev` 的构建任务。不要把“tag 发布更快”理解成首次全平台编译也只需 5 分钟；现有优化不降低发布编译质量，也不删掉任何发布平台。

## 验证

本地运行：

```bash
node --test scripts/release/resolve.test.mjs
```

上线后记录一轮成功 `dev` 预构建，再手动执行工作流，选择 `dev`、留空 `tag` 并勾选 `verify_only`。这会使用相同的产物选择、下载和完整性检查路径，并将完整附件重新上传为保留一天的验收 artifact，覆盖下载与上传两段传输，但不会创建或更新 Release。Summary 会记录从工作流创建到全部附件就绪的耗时。需要测试某个已有 tag 时可以同时填写 `tag`。

最后记录同源码 tag 的正式发布总耗时。确认 Summary 标明复用了预构建、desktop/android 均跳过、所有原有附件均存在，再判断是否达到 5 分钟目标。若耗时超过目标，先区分 runner 排队与附件下载/上传；不要用提前发布缺少附件的 Release 作为达标依据。
