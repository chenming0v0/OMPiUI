# 会话流量调查与修复计划

## 2026-10-11 调查

- 截图中的 3.33 MiB 是保留的 35 次会话 HTTP 请求的双向载荷合计，不能据此判断某个命令的单次大小。
- `trafficAudit/summary.ts` 把 `/commands/<命令名>` 也替换为 `:id`，导致不同命令无法区分。
- OMP RPC 的 `get_entries` 已使用 `since` 增量读取，但页面的 `refreshPiBranch` 每次读取最近 100 条、最多 2 MiB，然后在客户端合并。消息结束、工具完成、历史 head 变化等会重复触发这个读取。
- 流量审计只存于客户端内存。本次浏览器连接报 `unsupported Codex auth method: apikey`，未能读取截图对应的原始 35 条记录，因此不把复现比例冒充截图的实际组成。

## 实施计划

1. 排行榜保留命令名，保留会话等动态 ID 的归一化；展示双向累计、提交、接收、单次峰值。
2. 运行时维护少量最近分支快照的同步标识。客户端持有匹配快照且历史仅追加时，只返回新增条目及最新 checkpoint，并刷新向前分页游标。
3. 分支改变、历史重新播种、进程重启、缓存失效或增量超出分页限制时返回完整最新页。磁盘只读读取沿用现有行为，不创建 Agent。
4. 客户端保留已加载历史和更新的流式消息；同步基线不匹配时回退完整刷新。
5. 覆盖重复刷新、追加、分页、历史改写、多个客户端和响应竞争，用合成工具输出测量实际 JSON 字节数。

## 验证结果

已完成以上实现，改动保留在 `dev` 工作区。

### 可复现的流量对照

使用真实 `OmpRpcSession`、命令声明校验和 `branch.get` handler，RPC 底层使用确定性的测试数据，不启动模型或改写真实会话。初始 60 条工具输出，追加 17 条，连续读取 35 次：

| 项目 | 原完整分页 | 新增量分页 |
| --- | ---: | ---: |
| 请求参数与响应页 JSON 的 UTF-8 字节合计 | 10,327,334 B | 348,610 B |
| 换算 | 9.85 MiB | 340.44 KiB |
| 最终收到的历史条目 | 77 | 77 |

减少 **96.62%**。这是测试场景的量化结果，不代表截图中每个命令的实际占比。计量不包含公共 HTTP 响应封装、请求头、TLS 等开销；新响应的 checkpoint 和同步标识已计入。

复现命令：

```powershell
node --import tsx --test packages/omp-worker/src/omp/branch-traffic.test.ts
```

### 回归验证

- 前端相关 48 项测试通过：流量审计、排行榜、历史合并、增量读取、分页、流式消息和请求竞争。
- 协议与 worker 40 项测试通过；另有跨进程分页游标 2 项、服务端 SessionHost 15 项通过，合计 105 项不同测试。
- 协议、worker、app 构建通过；app/worker 类型检查及所改前端文件 ESLint 通过；`git diff --check` 通过。
- 分支回退、历史重新播种、未知/淘汰的同步标识和超出分页限制均返回完整页。无变化时只发送元数据和实时 checkpoint，不重发已落盘正文。
- 分页会保留最新 head 和同步基线；追加后重签客户端最早可见条目的向前游标。
- 历史快照仅缓存最近 4 组条目引用；历史重置时清空，不复制历史正文。
- 服务端只读浏览测试确认没有启动写入 runtime，也没有修改官方会话文件。

### 剩余限制与生效方式

- 截图对应的原始 35 条客户端内存记录未读取到，故无法给出那一批记录的准确命令占比。修复后的排行榜可以直接区分命令并展示提交/接收/单次峰值，便于下一次复现定位。
- 此次增量优化覆盖运行中的 OMP 会话；磁盘只读浏览沿用现有完整页逻辑。实时 checkpoint 仍可能包含正在生成的消息全文。
- 已完成构建，未打断正在工作的会话。服务端/worker 与页面应在下一次正常重启/刷新时一起使用新版本。
- 浏览器连接不可用，未做当前桌面上的实机视觉验收；排行榜组件测试和前端生产构建已通过。
- app 构建仍报告部分产物超过 500 kB 的分包提示；这属于静态资源体积，与本次会话接口累计载荷是不同计量对象。
